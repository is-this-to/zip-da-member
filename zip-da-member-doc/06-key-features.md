# 주요 기능

[README로 돌아가기](../README.md)

## 1. 회원 가입과 인증

일반 가입은 중복 검사 → 이메일 인증 → 약관 조회·동의 → 회원 생성 순서이다.

로그인 성공 시 Access Token은 응답에, Refresh Token은 HttpOnly Cookie에 저장된다. 비밀번호 재설정은 계정 존재 여부를 응답으로 노출하지 않는 흐름을 사용한다.

> **보안 적용 사항**
> - 비밀번호는 BCrypt로, 비밀번호 재설정 링크의 일회성 토큰은 SHA-256으로 hash해 저장한다. 
> - 로그인 Refresh Token은 HttpOnly Cookie로 전달하고 세션 테이블에 저장하며, 비밀번호 변경이나 재설정 후 기존 로그인 세션을 폐기한다.

## 2. 이메일 인증

이메일 인증은 회원가입과 로그인 후 비밀번호 변경에서 사용한다.

- 회원가입: 이메일 인증번호 발송 → 6자리 코드 확인 → 검증된 `verificationId`로 가입
- 비밀번호 변경: 로그인 회원의 계정 이메일로 코드 발송 → 인증 완료 → 현재 비밀번호와 새 비밀번호 확인
- 보호 정책: 인증 만료, 재발송 제한, 검증 시도 횟수 제한, 이미 완료된 인증 재사용 차단
- 개인정보 보호: 인증 대상 이메일은 원문 비교 대신 hash를 사용
- 별도의 스케줄러 실행: 매일 18:00(Asia/Seoul)에 실행되며, 실행 시점 기준으로 1일보다 이전에 만료된(`expires_at < now - 1일`) 이메일 인증 데이터를 물리 삭제

> **보안 적용 사항**
> - 인증번호는 `SecureRandom`으로 생성한 6자리 값이며, DB에는 BCrypt hash로 저장한다.
> - 인증 대상 이메일은 SHA-256 hash로 보관·대조한다.
> - 인증 목적을 회원가입과 비밀번호 변경으로 분리하고, 5분 만료·10초 재발송 대기·5회 검증 시도 제한·완료 인증 재사용 차단을 적용한다.
> - 비밀번호 변경용 인증은 로그인한 회원의 계정 이메일과 대조하며, 변경이 완료되면 활성 로그인 세션과 사용한 인증 레코드를 폐기한다.

## 3. 프로필과 파일

- 회원은 이름·닉네임·전화번호·프로필 이미지를 부분 수정할 수 있다. 
- 비밀번호 변경은 현재 비밀번호와 이메일 인증 결과를 확인하고 성공 후 Refresh Cookie를 제거한다.

> **보안 적용 사항**
> - MIME 유형은 파일의 데이터 형식을 나타내며 HTTP 요청의 `Content-Type`으로 전달된다. 서비스는 파일 용도에 따라 다음 검증을 적용한다.
>
> | 파일 구분 | 허용 MIME 유형 | 현재 검증 방식 |
> | --- | --- | --- |
> | 프로필 이미지 | `image/jpeg`, `image/jpg`, `image/png`, `image/gif`, `image/webp` | 허용 MIME 유형과 파일 확장자의 일치 여부 확인 |
> | 중개사 신청 서류 | `application/pdf`, `image/jpeg`, `image/jpg`, `image/png` | 10MB 제한, MIME 유형·확장자 일치 및 실제 파일 시작 바이트 확인 |
>
> - 전체 multipart 업로드는 파일당 10MB, 요청당 20MB로 제한한다. 
> - 프로필 이미지는 공개 파일로 관리한다. 중개사 신청 서류는 프로필 이미지와 분리된 MinIO 문서 경로에 저장하고 `PRIVATE` 파일로 관리한다.
> - 애플리케이션은 `PRIVATE` 서류에 대해서만 5분 동안 유효한 Presigned URL을 발급한다.

## 4. 중개사 전환

```text
┌─────────────────────┐
│ 초안 생성           │
└──────────┬──────────┘
           │ 정보 입력 · 문서 업로드 · OCR
           │ (제출 전까지 반복 수정)
┌──────────▼──────────┐
│ PENDING             │  신청 제출
└──────────┬──────────┘
           │ 관리자 심사 시작
┌──────────▼──────────┐
│ UNDER_REVIEW        │
└──────┬────────┬─────┘
       │        │
       │ 승인   │ 보완 요청 / 잘못된 자료
       ▼        ▼
┌────────────┐  ┌─────────────────────┐
│ APPROVED   │  │ REJECTED 또는       │
│ 중개사 전환│  │ INCORRECT_DATA      │
└────────────┘  └──────────┬──────────┘
                           │ 보완 후 재제출
                           └──────────▶ PENDING
```
- 제출 전 `PENDING`: `submitted_at`이 없으며 정보와 증빙 문서를 반복 수정할 수 있다.
- 제출 완료 `PENDING`: `submitted_at`이 설정되며 스케줄러의 자동 검증 대상이 된다.
- 외부 연동 미설정: 두 API 중 하나라도 설정되지 않으면 실행을 생략하고 `PENDING`을 유지한다.
- 자료 불일치: 두 검증 중 하나라도 불일치하면 `INCORRECT_DATA`로 전환한다.
- 외부 연동 오류: 불일치 없이 오류가 발생하면 `PENDING`을 유지하고 다음 실행에서 다시 검증한다.
- 검증 일치: 두 결과가 모두 일치하면 자동 승인하지 않고 `UNDER_REVIEW`로 전환하여 관리자 심사 대상으로 만든다.
- 보완·재제출: `REJECTED` 또는 `INCORRECT_DATA` 신청을 수정해 재제출하면 다시 제출 완료 `PENDING`이 된다.

### 4.1. Google Cloud Vision OCR 기반 안전한 서류 자동 입력

OCR이 활성화된 환경에서 사업자등록증과 중개사무소등록증을 업로드하면 Google Cloud Vision으로 문자를 인식하고 신청서의 주요 입력값을 자동 추출한다.

**처리 흐름**

`서류 형식 검증 → Vision 문자 인식 → 문서별 데이터 파싱 → 비공개 저장·체크섬 기록 → 빈 신청 항목 자동 반영 → 사용자 확인·수정`

| 구현 관점 | 적용 내용 |
| --- | --- |
| 외부 API 연동 | 이미지는 Google Cloud Vision 문서 인식 API로 처리하고, PDF는 Google Cloud Storage와 Vision 비동기 파일 처리 API를 사용한다. |
| 문서별 데이터 매핑 | OCR 원문을 문서 유형별 정규식 파서로 분석해 사업자등록번호·개업일자·대표자명 또는 중개사무소 등록번호·중개사무소명으로 변환한다. |
| 사용자 입력 보호 | OCR 결과는 신청서의 비어 있는 항목에만 반영하고 기존 입력값은 덮어쓰지 않는다. 신청인은 제출 전까지 자동 반영된 값을 확인·수정할 수 있다. |
| 장애 처리 | OCR 처리에 실패해도 검증된 서류는 저장하며 `FAILED` 상태와 실패 사유를 기록한다. PDF 처리에 사용한 Google Cloud Storage 임시 객체는 처리 종료 시 삭제를 시도한다. |
| 처리 추적 | OCR 원문, 추출값, 처리 상태와 완료 시각을 저장한다. |

> **보안 적용 사항**
> - 사업자등록증과 중개사무소등록증은 허용 형식·크기·MIME 유형·확장자와 실제 파일 시작 바이트를 검사한 후 OCR로 전달한다.
> - 본인이 소유한 수정 가능 상태의 신청에만 서류를 업로드할 수 있다.
> - 서류는 프로필 이미지와 분리된 MinIO 문서 경로에 `PRIVATE` 파일로 저장하고 SHA-256 체크섬을 기록한다.
> - 관리자용 서류 열람 API는 `SALES_ADMIN`과 `SUPER_ADMIN`으로 제한하며, 5분 만료 Presigned URL 발급 시 관리자·역할·대상 서류·IP·User-Agent와 Trace ID를 감사 이력에 저장한다.

### 4.2. 스케줄링 기반 공공데이터 자동 검증

- 스케줄러는 매일 02:00(Asia/Seoul)에 제출 완료된 `PENDING` 신청을 제출 시각이 오래된 순서로 최대 100건까지 자동 검증한다.
- 외부 API의 오류나 비정상 응답을 성공으로 처리하지 않으며, 모든 검증이 일치해도 관리자 심사 전에는 승인하지 않는다.

| 외부 연동 | 확인 내용 |
| --- | --- |
| 국세청 사업자등록정보 진위확인 API | 사업자등록번호·개업일자·대표자명 조합의 일치 여부와 사업자 상태 확인 |
| 국토교통부 중개사업소정보조회 API | 중개사무소 등록번호 조회 및 신청 등록번호와의 일치 여부 확인 |


## 5. 중개사 공개 프로필 관리

중개사는 고객에게 공개되는 중개사무소 정보와 소개를 직접 관리한다. 고객은 중개사무소명, 대표자, 연락처·주소, 영업 상태, 전문 지역과 영업시간을 확인할 수 있다.

- 중개사는 본인 프로필의 소개, 대표 이미지, 전문 지역과 요일별 영업시간을 수정한다.
- 프로필 수정은 인증된 해당 중개사 본인에게만 허용한다.
- 전문 지역과 요일별 영업시간은 중복 등록할 수 없다. 영업일은 시작 시각이 종료 시각보다 빨라야 하며, 휴무일은 시작·종료 시각을 저장하지 않는다.

## 6. 회원 제재와 중개소 운영 상태

### 6.1. 회원 계정 제재

관리자는 회원 계정 제재 및 제재해제를 할 수 있다.

- 계정 제재: 회원 상태를 `SUSPENDED`(정지)로 변경하고 활성 로그인 세션을 폐기한다.
- 계정 제재 해제: 다른 활성 `ACCOUNT` 제재가 없고 회원이 `SUSPENDED`(정지) 상태이면 `ACTIVE`(활성)로 복구한다.
- 감사 이력: 제재와 해제를 수행한 관리자, 역할, 사유, IP, User-Agent와 상태 변경 전후 값을 저장한다.

### 6.2. 중개소 운영 상태

- 중개소 운영 상태는 `ACTIVE`(영업중), `SUSPENDED`(휴업), `CLOSED`(폐업)로 관리한다.
- 매물 활동 제재: `ACTIVE`(영업중) 상태의 중개사만 매물을 등록·수정할 수 있다.
- 감사 이력: 관리자는 상태와 필수 사유를 입력해 변경하며, 변경한 관리자와 변경 전후 상태를 감사 이력에 저장한다.

## 7. RBAC 업무 매트릭스

### 7.1. 사용자 역할

| 업무 | 비로그인 | USER | AGENT | 추가 검증 |
| --- | :---: | :---: | :---: | --- |
| 약관·중복 검사·공개 중개사 프로필 조회 | 허용 | 허용 | 허용 | 공개 데이터 범위 |
| 가입 이메일 인증·회원가입·로그인·비밀번호 재설정 | 허용 | 차단 | 차단 | `!isAuthenticated()` 적용 API |
| 가입 전 프로필 이미지 업로드 | 허용 | 차단 | 차단 | 허용 MIME type과 크기 |
| 내 프로필 조회·수정·비밀번호 변경 | 차단 | 허용 | 허용 | JWT `sub`를 회원 ID로 사용 |
| 내 프로필 이미지 업로드 | 차단 | 허용 | 허용 | 파일 소유자와 카테고리 |
| 중개사 전환 신청 생성·수정·문서 업로드·제출 | 차단 | 허용 | 차단 | 신청 소유자와 상태 변경 |
| 최근 중개사 신청·내 신청 문서 조회 | 차단 | 허용 | 허용 | 신청 소유자 |
| 중개사 공개 프로필 수정 | 차단 | 차단 | 허용 | `agentId`와 인증 회원의 중개사 프로필 일치 |
| 중개사 대표 이미지 업로드 | 차단 | 차단 | 허용 | AGENT 역할, 파일 소유자와 카테고리 |

역할 검사만으로 소유권 검사가 끝나는 것은 아니다. URL의 `applicationId`, `documentId`, `agentId`가 로그인한 사용자의 데이터인지 Service 계층에서 다시 확인해야 한다.

| 회원 정지·정지 해제 | 허용 | 차단 | 허용 |
| 중개소 검색·조회 | 허용 | 허용 | 허용 |
| 중개사 신청 목록·상세·증빙 열람 | 차단 | 허용 | 허용 |
| 중개사 신청 보완 요청·승인 | 차단 | 허용 | 허용 |
| 중개소 영업 상태 목록·변경 | 차단 | 허용 | 허용 |

| 관리자 역할 부여·회수 | 차단 | 차단 | 허용 |

`SUPER_ADMIN`은 다른 역할의 모든 권한을 자동 상속하는 코드 구조가 아니라 각 `@PreAuthorize` 표현식에 명시적으로 포함된다. 새 관리자 API를 추가할 때 `SUPER_ADMIN` 포함 여부를 업무 정책에 따라 직접 결정해야 한다.

### 7.3. 인증과 업무 권한의 적용 순서

```text
Gateway JWT 검증
        │
        ▼
X-User-Id / X-User-Type / X-User-Role 생성
        │
        ▼
HeaderAuthenticationFilter
        │ Spring Authentication 생성
        ▼
@PreAuthorize 역할 검사
        │
        ▼
Service 소유권 · 계정 상태 · 신청 상태 검사
        │
        ▼
업무 처리 및 감사 이력 기록
```

회원 제재와 해제, 중개사 증빙 열람·승인·보완 요청, 중개소 영업 상태 변경, 관리자 계정·역할 변경은 처리한 사람의 ID와 역할, 처리 사유, IP, User-Agent 및 변경 전후 값을 감사 이력에 남긴다. 역할이 허용되더라도 필수 사유나 허용된 상태 변경 조건을 만족하지 않으면 업무 처리를 거부해야 한다.

> **보안 적용 사항**
> - Gateway가 유효한 JWT의 사용자 ID와 역할을 내부 헤더로 전달하면 Member의 `HeaderAuthenticationFilter`가 Spring `Authentication`을 구성한다.
> - Controller의 `@PreAuthorize`로 역할을 검사하고, Service 계층에서 리소스 소유권과 상태를 추가로 확인한다.
